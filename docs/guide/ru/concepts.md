# Модель и выполнение

## Request-сниппет и опасность кеша страницы

Request-сниппет предназначен для отдельного выполнения при каждом запросе страницы.
В отличие от Build, его результат не должен становиться общим замороженным значением.
Существующий кеш целой страницы может пропустить запуск сниппета при попадании в кеш.
Фоновое обновление не заменяет выполнение для каждого посетителя. Это может сломать
логику, зависящую от текущего времени, актуальных данных или отдельного запроса.
Работающая форма в браузере подтверждает её API-запросы, а не запуск серверного сниппета.

Перед включением кеша проверьте отсутствие Request-сниппетов во всей композиции:
привязках, вложенных чанках, целях Each и обеих ветвях условий. Если они есть,
оставьте кеш выключенным. Пока это ручная проверка автора. В
[принятом требовании](../../adr/0087-request-snippets-and-page-cache-guard.md)
зафиксированы будущие предупреждение в редакторе и проверка на backend/публикации;
они ещё не реализованы. SharedPublic/ParallelRead не отменяют это требование.

## Текущая реализация кеша

Серверный кеш Request-страницы явно включается в её редакторе. Начальный TTL —
60 секунд, допустимый диапазон — 1–3600 секунд. Сохранение меняет черновик,
публикация применяет политику. Каждый Request-сниппет отдельно разрешает публичный
кеш и задаёт допустимый возраст данных не меньше TTL страницы. Для запасного
результата вызовите `context.cache.bypass()`. HTTP сохраняет `no-store`.
Подробнее: [контракт кеша](../../arch/request-document-cache.md).

[Руководство](README.md) · [Рецепты](recipes.md)

Страница задаёт идентичность контента, URL — независимый объект маршрутизации,
релиз — неизменяемый набор опубликованных маршрутов и документов.
Шаблон владеет каркасом документа, чанк — переиспользуемым фрагментом.
TV определяют типизированные значения страниц и подготовленные ссылки на медиа.
Сниппеты готовят данные до композиции разметки. Аддоны владеют своими объектами
и могут регистрировать именованные операции API. Хуки выполняют проверки
и устойчивые реакции. Подробнее: [рендеринг](../../arch/rendering-and-publication.md),
[TV](../../arch/template-variables.md), [аддоны](../../arch/site-addons-contracts.md),
[хуки](../../arch/hooks.md).

API привязан к доверенному сайту. siteId/actorId и отмену задаёт хост. Вид шаблона/чанка/сниппета выбирается
группой API; бизнес-поле kind хуков и URL остаётся аргументом операции. Прикладные операции продолжают
проверять принадлежность страниц, URL и файлов.
sites.get и sites.list работают с текущим сайтом; sites.resolve не раскрывает
другой сайт. sites.create вызывает отдельную существующую операцию создания.
Пользователи админки — глобальные объекты установки; создание доступно в
«Настройки → Доступ → Создать пользователя» и консольном скрипте. У cms.adminUsers
нет метода для создания пользователей.
Новых ролей, RBAC и управления разрешениями расширений нет.

Результаты — отдельные readonly-данные без изменяемых ORM-объектов и save().
Моменты времени возвращаются строками ISO UTC; календарные даты остаются датами.
Большие целые значения/идентификаторы передаются без потерь десятичными строками.
Бинарное содержимое — массив целых байтов с byteSize и mimeType.
Отсутствующее поле остаётся отсутствующим, null сохраняется; false и 0
не заменяются значениями по умолчанию.

Build/Request не зависят от Static/Request для HTML и None/Api для браузера:

- Build выполняется при сборке и предпросмотре; результат фиксируется в артефакте.
  Повторная, неудачная и preview-сборка — тоже отдельные выполнения.
- Request — фаза отдельного выполнения для каждого запроса страницы с сохранённым
  кодом/планом и готовыми ресурсами. Существующие кеши целого документа CMS/CDN
  пропускают запуск; см. предупреждение выше. Для выполнения при каждом запросе
  такое повторное использование документа нужно отключить.
- Статический HTML может включать API-виджеты браузера. Это не превращает
  серверные сниппеты в отдельно загружаемые фрагменты и не открывает cms браузеру.

Чтение и команды разрешены в Build, Request и preview. Предпросмотр действительно
может менять данные. Всегда ожидайте завершения команд через await.
Общей гарантии exactly-once или транзакции вокруг рендера/публикации нет.
Завершённая команда сохраняется при последующей ошибке сниппета или публикации.
Тайм-аут, разрыв запроса и потерянный результат могут оставить неопределённый
исход: перед повтором проверяйте бизнес-идентичность и версию.
Идемпотентность определяется контрактом каждой команды.

Изменение прочитанных в Build данных само по себе HTML не пересобирает.
Зависимости данных и состава списков требуют явной пересборки.
Существующая snippets.update может перепубликовать зависимые опубликованные
страницы после полного успешного сохранения исходника. Это её отдельный
сценарий, а не общий механизм отслеживания данных.
Код опубликованного Request-сниппета фиксируется в приватном плане.

Скриптовые сниппеты используют ограниченный пул Worker в Build,
Request и preview. Каждый вызов получает новое изолированное окружение;
порядок вызовов и семантика команд сохраняются. Оператор задаёт размер пула,
очередь и дедлайны: [ограничения и жизненный цикл](../../arch/snippet-worker-pool.md).
Пул сам по себе не включает кеш документов. Независимые сниппеты с явной отметкой
`ParallelRead` выполняются параллельно в установленных лимитах, включая безопасные
чанки и Each. Их CMS-клиент запрещает команды. Вызовы без отметки остаются барьерами
порядка. Подробнее:
[параллельное выполнение](../../arch/parallel-snippet-execution.md).

Составная операция аддона и CMS принадлежит прикладному сценарию и использует
явные порты. Последовательные вызовы не образуют атомарную транзакцию.
До предоставления составной команды её поставщик обязан определить атомарность
и восстановление; сессий БД в cms-контрактах нет.
Хуки сохраняют свои существующие разрешения, порядок доставки и правила повторов.
Новая модель API их автоматически не заменяет.
