# CMS 0.14.0 process allocation verification

Date: 2026-11-13. Synthetic isolated environments only. No existing installation
was upgraded and no release was published.

## Boundaries

The native integration creates two empty synthetic sites, publishes actual
ZaryaBasic Request pages, starts the real supervisor and site pools, authenticates
through HTTP, and creates real complete archives through all three capture modes.
Host headers `one.test` / `two.test` select registered authorities without changing
the hosts file. Unknown authorities return 404. No business add-on is installed.
The test-only private worker harness counts admitted requests, actual composition
calls and process CPU deltas; its bounded freeze runs inside published Request
composition. Production has no freeze/diagnostic endpoint or worker command.

The shared gate is checked with an admitted writer in a distinct site process:
capture waits, another HTTP write returns 503, and capture proceeds after that
writer releases admission. Read traffic continues during capture after the
intentional initial drain. Three dump branches retain the requester, never borrow
another site, and restore exactly the borrowed target-site worker.

The load regression found premature provider shutdown while retiring a worker:
Nest closed its parsed-plan cache before an admitted response completed. Serving
workers now close/drain the private HTTP server before destroying providers.
Continuous neighboring requests during lending permanently cover the failure.
An unauthorized POST with a declared but unsent body is rejected before body
admission. Resource changes use expected versions and reject active capture.

## Measured freeze isolation

Windows native Node.js 26.7.0, MongoDB 9.0.8 in a dedicated replica-set container
with a one-CPU quota. The host has 20 logical CPUs; Docker Desktop reported 20
CPUs and approximately 46.8 GiB. The generator shares the host and is excluded
from the measured worker CPU deltas. There is no keep-alive connection affinity.
Equal 2/2 pools warm up for 30 seconds with two request loops per site, then A/B
use 1/2 processes and two/four request loops with 200 ms pacing for 120 seconds.
A's sole serving event loop blocks for five seconds after 40 seconds. This is
controlled headroom, not a claim about maximum production throughput.

| Neighbor B interval | Requests | Errors | p50 ms | p95 ms | p99 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Before A freeze | 708 | 0 | 17.14 | 19.63 | 21.20 |
| During A freeze | 88 | 0 | 15.06 | 17.79 | 20.69 |
| After A freeze | 1320 | 0 | 16.90 | 20.26 | 22.77 |

Measured freeze: 5000.1 ms. Allowed neighboring p95 increase was
`max(20% of baseline, 20 ms)` = 20 ms; observed p95 did not increase. A completed
1014 real renders using 12048 ms CPU; B's two workers each completed 1058 renders,
using 7953 and 7641 ms CPU. The equal-pool warm-up reached all four processes with
134 real renders each, within the predeclared two-request balancing tolerance.
The deterministic ownership/freeze check also swaps A/B's 1/2-process allocations.
Counts show request-level balancing for this workload,
not equal CPU consumption or exclusive core ownership. Core samples remained
current in the authenticated browser during the freeze; screenshots correlate
the native host counters with the separate private worker observations.

A separate ten-second shared-database pressure run used 16 B loops without pacing
and reduced only the labelled test database container to 0.25 CPU. It completed
2000 requests without errors: p50 88.01 ms, p95 109.29 ms, p99 180.09 ms. The quota
was restored. This illustrates shared-resource contention and is not evaluated
against the controlled-headroom freeze tolerance.

Run with an explicitly isolated `ZARYA_TEST_MONGO_URI`, the optional local Chrome
executable in `ZARYA_TEST_BROWSER_EXECUTABLE`, and `ZARYA_TEST_PROCESS_LOAD=1`:

```sh
npx vitest run --config vitest.config.integration.ts test/integration/site-process-supervisor.integration.spec.ts
```

The optional `ZARYA_TEST_PROCESS_LOAD_DB_CONTAINER` must identify a container
labelled `zarya.task=0140-process-tests`; no unrelated container is accepted.
The fixture removes only its random `zarya_test_*` database and checked temporary
storage, closes listeners/workers, and restores the test database quota.

## Docker, database and administration

The real two-site supervisor/capture fixture also ran in a six-CPU, 8 GiB Linux
container against isolated MongoDB. The managed Unix helper was separately run
against a dedicated Compose project: it applied and observed database/CMS limits
1.2/2.8 CPU, rejected a wrong key and a caller-supplied container identity, and
observed the same quotas after app-container recreation from its persisted
override. Fractional quota and narrower affinity translation have focused tests.
Quota control does not claim exclusive physical cores.

The MongoDB 8.0.38 → 9.0.8 synthetic volume upgrade retained FCV 8.0, required
validators, unique indexes and exact signed Int64 bytes; a snapshot/majority
transaction committed. See [upgrade evidence and procedure](../arch/mongodb-9-upgrade.md).
Existing complete dump/create/selected-site restore scenarios pass on the new
image. Historical JSON-LD scenarios elsewhere in that integration file are not
included in that focused claim.

The production administration bundle displays `CMS Zarya v.0.14.0` from root
metadata. Real authenticated Chrome checks cover resource controls, logical-CPU
charts and document overflow at widths 320, 375, 390, 393, 402, 414, 430, 440, 575,
576, 767, 768, 991, 992, 1199, 1200 and 1440 pixels. Chrome is not proof of Safari
device compatibility. CPU chart state stays in browser memory only.

Both final local Docker images (`cms-zarya-app:0.14.0` and
`cms-zarya-cloudflare:0.14.0`) passed the actual-built-version check. All twelve
packaged migration files in the HTTP image matched source SHA-256 bytes exactly
and contained LF without CR bytes. Images remain local verification artifacts.

Focused domain/application/adapter/composition tests cover allocation examples,
fractional remainder, stale edits, dump failures/cancellation, capacity deadlines,
replacement failure, shared invalidation, telemetry baselines/resets/session loss,
release consistency and add-on replica refresh. Required architecture, typecheck,
format, lint and build checks accompany these; the full suite is not requested.

## Fork revision, 2026-11-14

ADR 0083 replaces the estimated memory/connection admission policy. Twenty
explicitly selected domain/application/adapter/composition/settings/architecture
test files passed (79 tests); the full suite was not run. This includes saving
22 processes through both application and real allocation-persistence adapters,
explicit database placement, retained counts after moving a database remote,
borrowed-pool restoration after requester death, delayed crash replacement,
cancellation acknowledgements and interrupted-capture write-gate recovery.

The real two-site MongoDB/browser fixture passed with direct coordinator-owned
capture children in all applicable modes. Private lease observations verified
the actual coordinator parent and distinct serving operation owner. Inline
capture created no child. The browser saved six workers against a five-CPU
recommendation, and a request for 22 reached the HTTP boundary; its synthetic
server rejection remained beside Save while preserving edited/saved/running
distinctions. There is no memory/connection process-limit field or client block.
CPU-tab/grid/card checks and the existing viewport matrix passed.

A separate deterministic fault test uses actual OS processes: killing the
serving requester cancels/reaps the coordinator's capture child, removes staging,
reconciles only its dead capture operation and reopens writes. A changed lock or
interrupted restore is rejected; recovery never clears a live owner's gate.
The child's actual parent, operation owner and archive completion checks remain
independent.

Earlier throughput/latency measurements above belong to the preceding revision
and were not rerun as new performance claims. The current work prepares only
the unreleased 0.14.0 branch and a local installation update.

## Resource form request lifecycle, 2026-11-14

Nine focused client/preview tests passed, including deadlines covering both
response headers and body, transport that ignores abort, and late rejection
observation. The allocation deadline remains 120 seconds; actual-state reads
are bounded to 10 seconds. A deadline releases apply/global-busy state before
reconciliation rather than retaining it during another pending request.

The isolated MongoDB/Chrome fixture passed with a real ten-worker allocation.
It checks a circular overlay during application, spinner placement inside the
visible scrolled viewport, removal after completion, and actual saved/running
counts. A held background read leaves editing enabled; its obsolete response
cannot overwrite a newer successful save. A held response after a successful
server-side change exercises the allocation deadline and read reconciliation:
the client confirms the applied state and remains editable. Existing HTTP-error
checks preserve edits and display feedback beside Save. Typecheck, format, lint
and administration builds passed. No full-suite or new performance claim is made.
