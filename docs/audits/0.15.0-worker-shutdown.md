# CMS 0.15.0: shutdown after administration disconnects

Verified locally on Windows with Node 26.7.0, real MongoDB 9.0.8, Chrome and native
site/administration forks. No production deployment was performed.

## Defect and correction

A browser could disconnect while the coordinator awaited session checks or site
routing. Dispatch then acquired a process admission and attached response
finish/close listeners after the close event had already happened. That admission
was never released. The process pool waited for a nonexistent active request until
its drain deadline. Both site and administration pools used the same mechanism;
the administrative pool caused the observed delay after leaving settings.

HTTP admission now checks aborted requests and destroyed/already completed
responses before acquiring the process lease. The check, acquisition and listener
registration are synchronous, so a network event cannot intervene between them.
The shared HTTP adapter owns this rule for both pools. Normal completion and
synchronous proxy setup failure retain exactly-once release.

The worker teardown, database lifecycle, IPC protocol, normal drain deadline and
20-second add-on update deadline are unchanged. There is no extra delay, forced
successful exit, suppressed shutdown error or larger timeout.

## Regression evidence

The [deterministic HTTP test](../../test/adapters/process-request-admission.spec.ts)
holds asynchronous dispatch, disconnects the client, observes response closure,
then resumes dispatch. Before the fix, it acquired an unreleasable admission;
afterward it acquires none. Neighboring cases verify release on ordinary response
completion and synchronous proxy setup failure.

The [full shutdown test](../../test/integration/fork-shutdown.integration.spec.ts)
creates isolated published sites, opens General and Calibration with Chrome,
closes the browser, and awaits actual coordinator/worker cleanup. It failed before
the fix with the drain deadline; after the fix cleanup succeeds within five
seconds. The test uses native workers without diagnostic shims or a business
add-on. Existing proxy cancellation/retry and rolling replacement/forced-stop
checks remain applicable.

The consuming Bloglist installation is verified separately after transferring and
building the fixed engine. Its users, site data, selected immutable add-on runtime
and private settings are preserved; only transient authentication/session locks
are excluded from document fingerprint comparisons.

The adjacent long-request drain test also exposed an existing composition error
when public serving had no administrator boundary: calibration providers still
required the administrator session service. PublicHttpModule now registers that
administration-only graph only with adminAuth. A separate
[composition regression](../../test/infra/public-calibration-composition.spec.ts)
failed before the correction and passes alongside local-operator resource
composition. This restores the public-only path used by the long-request test.

## Consuming installation verification

The existing Bloglist installation was rebuilt from the fixed 0.15.0 source. The
same Chrome scenario that previously reached the drain deadline now completes
shutdown in 89 ms; a repeat against the final build completed in 92 ms. General
and Calibration loaded with three CMS processes and no browser exceptions.
Document fingerprints retained both users, 500 clusters, three pages and the
selected Bloglist runtime; 20 protected content/runtime/settings files matched.
The CMS was left stopped for IDE startup and its MongoDB dependency kept running.
The final isolated integration batch passed both administration shutdown and
active long-request drain during pool replacement.
