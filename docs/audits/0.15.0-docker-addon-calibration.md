# CMS 0.15.0: calibration with real Docker CPU quotas

Executed locally on 2026-11-16 against branch `0.15.0`. This is functional
verification of enforcement, application and recovery, not a production sizing
recommendation. No released image, production installation or existing site data
was replaced.

## Environment and workload

- Docker Desktop 4.88.1, Linux Engine 29.7.2 / API 1.55, WSL2, 20 visible CPUs.
- Current CMS Dockerfile `build` stage, Node 26.7.0, npm 11.19.0.
- MongoDB 9.0.8, image digest
  `sha256:1444adda2e4b8d6a0d7f242a625d834a78d6e3aa6e4ed1b0b4c2dab2318c5e3d`,
  separate disposable replica set and database, 0.25 GiB WiredTiger cache.
- Separate CMS and resource-helper containers. The unmodified compiled
  `dist/resource-helper.js` used the real Docker Engine socket, scoped by Compose
  project/service labels. There was no quota protocol double.
- The helper shared the CMS network namespace for trusted loopback HTTP, while
  retaining its own PID namespace and cgroup. Its generator was outside the CMS
  container CPU quota, on the same VM; no exclusive physical CPUs were reserved.
- Two isolated published sites: Events 0.4.4 on the first, Bloglist 0.1.0 on the
  second. Native serving/control workers ran, without the resilient-worker shim.
- Equal traffic shares. Each Events visit loaded static HTML then the real public
  sessions GET with the resolved page and UTC window. Bloglist has no declared
  public API, so its visits loaded published HTML. Business collections were empty.
- Completion search: shared CPU budget 3, concurrency 2, process candidates 1/2,
  pool candidate 5, database CPU step 0.5, warmup 1 s, probes/confirmation 2 s,
  overall budget 90 s. The initial pool of 10 also participated in the reference
  and subsequent coordinate search.

## Observations

The expanded test passed in 143.52 seconds (147.28 seconds including collection).
An earlier, shorter version of the same real-Docker test also passed.

| Check | Observed result |
| --- | --- |
| Original allocation | DB 1 CPU, CMS 5 CPU; Events 2 processes, Bloglist 1; pool 10 |
| Actual search limits | DB 0.5/1/1.5/2/2.5 CPU paired with CMS 2.5/2/1.5/1/0.5 CPU |
| Completion | `Completed`, `restored: true`; original quotas, processes and pool restored before application |
| Confirmed recommendation | DB 1 CPU, CMS 2 CPU; Events 1 process, Bloglist 2; pool 10 |
| Explicit application | Real quotas, ready process counts and pool matched the recommendation; persisted Compose override matched both CPU limits |
| Cancellation | During active real load at DB 1 / CMS 3 CPU, processes 1/1 and pool 1; returned `Cancelled`, restored the applied recommendation including pool 10 |
| Generator failure | Killed exactly one real load worker with SIGKILL at changed quotas/pool; returned `Failed`, no winner, `restored: true` |
| After failure | Real quotas, processes and pool restored; generator reaped, new resource write admitted, both published pages still answered 200 |
| Final cleanup | Original DB 1 / CMS 5 CPU, processes 2/1 and pool 10 restored; temporary containers, database, network and control volume removed |

The test independently inspected Docker `HostConfig.NanoCpus` and compared the CMS
quota with `/sys/fs/cgroup/cpu.max`. Host-side `docker inspect` also observed the
0.5 CPU CMS / 2.5 CPU MongoDB probe; `cpu.max` was `50000 100000` in CMS. MongoDB's
cgroup was checked separately. Every retained measurement's observed limits
matched its requested configuration. Both sites answered 200 during polling.
The sessions step recorded successful real HTTP requests. All 15 completion
measurements had zero errors. The final confirmation recorded 249 visits,
123.70 visits/s and p95 21.10 ms; short intervals, trivial pages, empty business
data and shared VM contention make these numbers unsuitable for capacity planning.

The failed run retained the diagnostic `Unexpected end of JSON input` after the
generator's forced exit. Resource restoration succeeded despite that imprecise
transport diagnostic; clearer classification of that message remains a limitation.

## Production Compose correction

The check exposed `network_mode: none` on the production helper: its loopback
generator could not reach the CMS listener. The production helper now uses
`network_mode: service:app`. The application waits for the private helper socket
before starting HTTP, and its reverse Compose dependency on the helper was removed
to avoid a cycle. The helper's HTTP control surface remains a private Unix socket.
This changes the deployment definition; no production deployment was performed.

The focused Compose integration test failed with `none`, then passed with the
corrected configuration through Docker Compose's actual JSON renderer. Existing
bounded helper-readiness tests passed. The real quota test used the corrected
network topology.

## Reproduction

Use [the opt-in Docker fixture](../../test/fixtures/docker-calibration.compose.json)
and [the real quota test](../../test/integration/docker-addon-calibration.integration.spec.ts).
The fixture deliberately grants Docker access to the test observer and has no
public port mapping. It is for disposable QA only, never an existing installation.
Keep the runtime directories and evidence output outside the clean CMS distribution.

Build the current image's `build` target and set these environment variables:

```text
ZARYA_TEST_DOCKER_PROJECT=zarya-calibration-qa-<unique-alphanumeric-suffix>
ZARYA_TEST_CMS_IMAGE=cms-zarya-build:0.15.0
ZARYA_TEST_CMS_ROOT=<absolute checkout path>
ZARYA_TEST_EVENTS_ADDON_DIRECTORY=<absolute immutable Events runtime directory>
ZARYA_TEST_BLOGLIST_ADDON_DIRECTORY=<absolute immutable Bloglist runtime directory>
ZARYA_TEST_DOCKER_EVIDENCE_ROOT=<absolute private output directory>
```

Then, with `docker compose -f test/fixtures/docker-calibration.compose.json`:

1. Start only `app`. In it generate `/run/zarya/key` as 32 random bytes encoded
   in hexadecimal, mode 0600. Do not print the key.
2. Start `mongo` and `resource-control`. Initiate the disposable `qa-rs` replica
   set with member `mongo:27017`, then wait for a writable primary and the private
   resource socket.
3. In `app`, execute exactly:

   ```sh
   npx vitest run --config vitest.config.integration.ts \
     test/integration/docker-addon-calibration.integration.spec.ts \
     -t 'changes real Docker quotas'
   ```

4. Review the private `docker-calibration.json` evidence. Run the matching Compose
   project's `down --volumes` in a finally block even if a check fails.

The test removes only its own guarded `zarya_test_*` database and temporary files.
Existing `bloglist_trial`, its MongoDB service, users and add-on data were untouched
and its database service remained healthy after QA cleanup.
