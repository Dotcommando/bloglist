# Resource administration security review

Reviewed the 0.14.0 fork supervisor, resource administration HTTP endpoint, CPU
telemetry WebSocket, private worker listener and Docker resource helper. This is
a focused regression review, not a claim that the whole CMS has no vulnerabilities.

## Entry points

| Entry point | Authority and effect |
| --- | --- |
| `GET /api/admin/installation/resources` | A validated active installation administrator can read the allocation; anonymous requests receive 401. |
| `POST /api/admin/installation/resources` | The same authority plus trusted Host, same Origin and `X-Zarya-Admin: 1` are required before parsing JSON. This single operation changes site processes, site pool size and, when configured, managed database CPU. |
| WebSocket `GET /api/admin/installation/cpu` | Trusted Host/Origin and a validated administrator session are required before upgrade; authorization is checked again during the subscription. The channel accepts no mutation commands. |
| Private worker HTTP listener | A separate coordinator-generated secret is required; knowing the port or possessing an ordinary admin cookie is insufficient. |
| Unix socket `GET/PUT /limits` | Not a TCP endpoint. Requires the separate helper key and filesystem socket permissions; ordinary CMS admin sessions do not authenticate here. |

Directus code or vulnerable package exists in Zarya.

## Findings and changes

No anonymous resource mutation was reproduced. Existing session validation,
same-origin checks and the helper credential already reject unauthenticated
access. Both `GetInstallationResources` and `ChangeInstallationResources` now
explicitly require an active installation administrator; HTTP and WebSocket
boundaries apply the same policy before consuming request bodies/subscribing.

Currently supported administrator profiles already require empty site assignments
and authentication already rejects blocked accounts. Tests supplying blocked or
site-scoped profile doubles verify defense in depth for these global operations;
they do not demonstrate a reachable privilege-escalation exploit in the current
production composition.

The HTTP resource adapter previously admitted non-finite/negative database CPU
numbers and zero site processes into the application boundary. The application
already rejected them. The adapter now rejects them directly, matching the
approved numeric invariants without imposing a new worker, memory or connection
cap. The regression first reproduced the adapter accepting an overflowing JSON
number, then passed after the boundary validation was added.

The Unix helper remains a separate, narrowly scoped host integration. It listens
on a private filesystem socket, uses a separate random 256-bit key, compares
credential digests in constant time and addresses registered Compose services.
An ordinary admin cookie/token cannot authenticate to it. The Linux regression
starts the actual compiled helper with a synthetic Docker HTTP socket; it mounts
no real Docker socket and makes no real container changes. It checks socket mode,
duplicate Authorization headers, rejection before upload/Docker access, strict
payload keys and a successful authorized synthetic update.

## Focused regression files

- `test/app/installation-resources.spec.ts`: authentication and installation-wide
  authority before site enumeration/resource reads or writes.
- `test/adapters/admin-resource-security.spec.ts`: forged identities, CSRF,
  duplicate/oversized headers, unfinished 1 GiB upload, strict JSON/numeric
  validation and sanitized failures.
- `test/adapters/admin-cpu-security.spec.ts` and
  `test/adapters/admin-cpu-telemetry.spec.ts`: WebSocket origin/session checks,
  live authority/boundary changes, read-only channel and subscription cleanup.
- `test/adapters/resource-helper-security.spec.ts`: actual helper entry point on
  Linux with an isolated fake Docker endpoint; skipped on Windows.
- `test/integration/resource-security.integration.spec.ts`: real HTTP composition,
  real session login/logout, all three mutation classes, private worker denial,
  route variants and public/private file separation. Uses only an explicitly
  configured MongoDB and a guarded random `zarya_test_*` database.
- Existing authentication regressions cover rotating login identifiers and
  account/session invalidation. No live third-party service is called by tests.

Run explicit files only. Execute the Unix-helper test on Linux after building
`dist/resource-helper.js`; a Windows skip does not count as verification.

## Executed verification

On 2026-11-15, the nine selected application/adapter/composition/authentication
files passed 52 tests. The focused architectural import check passed separately.
The real-session/private-file integration test passed against a guarded random
test database. The actual Unix-helper test passed inside an isolated Linux
container with networking disabled and no host Docker socket. Total: 55 passing
focused tests; the full suite was not run. Server type checking, server build,
root formatting, root linting and whitespace checks passed.

Installation checks additionally confirmed that unauthenticated GET and POST
resource requests return HTTP 401 after deploying the updated test image.
Installation addresses, credentials, per-process evidence and load measurements
remain in private installation reports rather than this distribution.

## Distribution behavior

`SiteProcessPool.select(siteId)` advances a separate cursor for each site and
selects the next ready, non-retiring, non-exited process for each HTTP request.
This is round robin; it is not least-connections scheduling or CPU affinity.
Keep-alive connections at either HTTP hop do not make a browser session sticky
to one site worker. Replacement workers enter rotation only after readiness,
and retiring workers finish their admitted requests without receiving new ones.
