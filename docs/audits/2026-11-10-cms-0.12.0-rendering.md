# CMS 0.12.0 rendering and execution isolation

Measured on 2026-11-10 in an isolated synthetic installation, Node 26.7.0,
Windows, local MongoDB. No installation content, business add-on registration or
private configuration was added to the CMS distribution. All test listeners,
contexts, children and test databases were closed/removed after the run.

## Method

The fixture has two Request pages with 120 and 60 Markdown paragraphs, escaped
HTML, compiled CSS and identical published data. The homepage enables a
20-second SharedPublic cache; the secondary page executes without document
reuse. Component comparisons alternate before/after order and assert exact
result equivalence after each sample. Timings are separate comparisons, not
additive spans or a cumulative whole-site speedup.

The catalog and HTML baselines use compiled 0.11.0 code from commit `1573fe8`.
Other comparisons use the current shared rendering pipeline with only the
tested preparation/fingerprint disabled. Activation reads, storage, instrumentation
and connection settings stay the same. Forced misses purge the document cache
and keep verified plans warm. They are distinct from the real idle sample below.

All paired outputs matched; no operation errors occurred. The verified plan was
51,757 serialized UTF-8 bytes; its retained hexadecimal fingerprint adds 64
ASCII characters (128 UTF-16 content bytes, plus object/accounting overhead).
Prepared HTML/CSS metadata and page Markdown have bounded plan-cache accounting.
Final HTML minification still runs for dynamic output. The HTML change primarily
reduces hash extraction cost; it does not remove all document processing.

327/15, HTML 391/362, style hashes 185/109, Markdown 295/141, fingerprint hits
201/175, fingerprint misses 518/500. Windows CPU samples are coarse; the small
differences do not establish a precise CPU percentage or per-stage allocation.
An initial 20-sample fingerprint-miss run had a slightly slower median; the
larger interleaved run above resolved that uncertainty. No cumulative gain is
claimed from these independent numbers.

First HTTP requests in a new serving composition took 32.748 ms (homepage miss)
and 17.206 ms (secondary). After warming the homepage and leaving HTTP idle for
20.5 seconds, it returned a real miss in 23.436 ms; the secondary returned in
12.520 ms. Both returned 200. These are single observations, not percentile
estimates or before/after cold-start claims.

## Public HTTP during dump capture

Both exports included the same 32 MiB deterministic binary media file. The
baseline uses the original parent-process capture implementation and exclusive
maintenance behavior; the new implementation uses the real compiled child with
its own bounded MongoDB pool and the serving composition's maintenance gate.
The temporary HTTP client alternates the homepage and secondary page at
concurrency two, with a five-millisecond gap between rounds, throughout capture.
Samples include cache hits and real generation; the initial maintenance purge
also produces a homepage miss.

| Export | Duration | HTTP samples / outcome | HTTP median / p95 | Event-loop p95 / max |
| --- | ---: | --- | ---: | ---: |
| Full, parent baseline | 1698 ms | 640 / all 503 | unavailable | 10.568 / 14.795 ms |
| Full, child process | 2259 ms | 198 / all 200 | 10.392 / 13.349 ms | 20.775 / 25.625 ms |
| Files, parent baseline | 1488 ms | 568 / all 503 | unavailable | 10.478 / 13.935 ms |
| Files, child process | 2099 ms | 186 / all 200 | 10.390 / 13.256 ms | 20.972 / 25.706 ms |

Full-child samples contain 98 hits (p95 13.340 ms) and 100 generated responses
(p95 13.594 ms). Files-child samples contain 91 hits (p95 13.059 ms) and 95
generated responses (p95 13.947 ms). No HTTP errors occurred in either child
variant. The baseline's fast 503 responses are rejection, not useful latency.
The child export takes longer while serving real requests; this change protects
availability rather than promising faster exports.

Parent sampled CPU/peak RSS: full baseline 2765 ms / 384 MiB, full child 876 ms /
335 MiB; Files baseline 2266 ms / 394 MiB, Files child 687 ms / 374 MiB. Child
CPU/RSS was not included in these parent figures. Event-loop sampling resolution
was ten milliseconds. Increased parent-loop work in the child variants includes
the successful public rendering that the old gate rejected.

## Simultaneous refresh and foreground traffic

Thirty-two synthetic retained entries reach their refresh window about one
second after admission (TTL 21 seconds). A warm production Worker regenerates
the same published page. Foreground traffic continues on the real public HTTP
composition for approximately 1.9 seconds, covering the burst. The comparison
executes the same generation inline as an experimental baseline; production
never falls back to inline background regeneration.

| Execution | HTTP samples / outcome | HTTP median / p95 | Event-loop p95 / max |
| --- | --- | ---: | ---: |
| Experimental inline | 222 / all 200 | 9.055 / 11.942 ms | 15.892 / 90.112 ms |
| Bounded Worker | 236 / all 200 | 8.958 / 10.942 ms | 15.679 / 21.021 ms |

Worker admission accepted 17 refreshes and refused 15 before dispatch; all
accepted jobs completed, with no failures and no remaining active/queued work.
Refused entries retain their original deadline and ordinary miss behavior.
The inline variant finished all 32, because individual timer callbacks could
complete sequentially on its event loop. Thus these are admission/contention
observations, not an equal-work CPU-throughput comparison. Worker count remained
one; no additional database pool or nested Snippet pool was created by refresh.

The Worker run includes 117 hits (p95 10.624 ms) and 119 generated responses
(p95 10.954 ms). Parent-process sampled CPU/RSS was 1000 ms / 440 MiB versus
984 ms / 425 MiB inline. Worker memory contributes to process RSS; these figures
do not demonstrate reduced total CPU or memory. They demonstrate bounded
admission and responsive foreground requests for this fixture and host.

## Correctness coverage and limits

Focused application/adapter tests cover generation fencing, exact refresh timing,
short TTL, eviction, late results, fallbacks, queue/admission bounds, independent
cancellation, startup failure, crash, malformed messages, timeout, shutdown,
staging ownership and cleanup. Real-composition regressions cover publication,
catalog membership, restore invalidation, full/category/add-on archives and
public delivery during both full and Files capture. The browser checks warning
thresholds, both interface languages, narrow viewports and the built CMS version.

These measurements use one local serving process and a small synthetic dataset.
They do not prove capacity on a one-core production host, all native add-on
providers, larger installations or concurrent independent HTTP writers. Cache
coordination remains process-local. Dump consistency retains the documented
single-writer/quiescent-external-writer requirement. Performance of a real site
requires its own private measurements; no production deployment was performed.
