# CMS 0.12.0: Request rendering performance and administration scope

The owner requested the first five workstreams for version 0.12.0 on
2026-11-09 and added dump-process isolation on 2026-11-10. On 2026-11-10,
the owner specified Worker-thread cache refresh exactly 20 seconds before expiry.
The later clarification canceled the Snippet/Chunk drawer workflow. This document
records the agreed release scope and acceptance criteria. Implemented decisions
are described in ADRs 0070–0075; measurements are recorded in the
[synthetic verification report](../audits/2026-11-10-cms-0.12.0-rendering.md).
Implementation does not imply deployment to production installations.

The objective is to reduce actual Request-page generation time on HTML-cache
misses and reduce visitor waiting at cache renewal. Preserve publication,
access, tenant-isolation and freshness guarantees. Keep the CMS distribution
generic, with empty business add-on registries.

## Workstreams and order

Implement and measure each workstream separately, in order 1, 3, 2, 4, 5.
Do not combine several optimizations into one before/after comparison.
Workstream 6 is also required for 0.12.0 and has independent implementation and
verification; it does not depend on completion of the rendering optimizations.

### 1. Reuse the verified published-page catalog

Avoid repeating full immutable-release file verification merely to determine
which requested pages are published. Retain a verified catalog qualified by
site and release identity, behind the CMS publication boundary. Add-ons continue
using explicit CMS ports; they do not inspect publication files or collections.

Acceptance:

- Initial admission performs the required integrity and ownership checks.
- Active-release selection and applicable site/add-on access checks remain live.
- Single-page, full-site and routing-only publication select distinct release
  identities; drafts do not change cached public state.
- Dump maintenance invalidates retained and pending work, including restoration
  of an identity previously seen in the process. Late reads cannot repopulate it.
- Retention and in-flight work are bounded. Oversized catalogs remain usable
  without retention. Diagnostics distinguish hits, misses, evictions and
  admission refusals without exposing private content.
- No change to per-page Events limits, result completeness or isolation.

### 2. Reduce whole-document HTML processing

Prepare immutable HTML portions and eligible inline-style hashes at publication
time. Reduce repeated full-document minification and parsing on Request misses,
while retaining correct handling of dynamic output.

Acceptance:

- Preserve HTML escaping, significant whitespace, comments with required
  semantics, attributes, `pre`/`textarea` content and browser behavior.
- CSP hashes describe the exact style bytes sent to the browser. Dynamic style
  content cannot reuse an unrelated static hash.
- Preserve minified production output, asset injection, content lengths,
  Markdown representation and the existing shared/page CSS contract.
- Compatibility with retained plans is explicit; no incoming request compiles
  CSS/JS or reruns Build loaders.

### 3. Retain the immutable plan fingerprint

Compute the verified plan/assets fingerprint once at plan admission rather than
serializing and hashing the entire stored plan before every HTML-cache lookup.

Acceptance:

- Identity covers the same verified inputs as today; distinct plans/assets,
  releases and sites cannot collide through omitted inputs.
- Mutable caller copies cannot change a cached fingerprint's meaning.
- Typed request values, path, language and representation still participate in
  the rendered-document key. Referral and unfamiliar GET metadata retain the
  current normalization semantics.
- Fingerprints follow plan eviction, publication and dump-maintenance fences.
- Measure both HTML-cache hits and misses, including fingerprint memory cost.

### 4. Move immutable rendering work to publication

Identify Markdown transformations, template preparation and data preparation
that depend exclusively on published inputs. Freeze their results in the
publication plan, leaving current Request data and its dependent markup for
runtime execution. Start with measured work rather than speculative AST caches.

Acceptance:

- Preserve explicit Build/Request phases, frozen values and conditional inputs.
- Live schedule data, time-dependent results, access checks and request-private
  values cannot become publication-time constants.
- Preserve escaping, sanitization, typed parameters, null/default distinctions,
  previews and site/page/language scope.
- Single-page publication retains other published pages correctly; full-site
  publication and dump restoration remain equivalent at observable boundaries.
- Plan-format changes include documented compatibility and upgrade behavior.

### 5. Refresh eligible HTML before expiry

Add bounded background refresh for existing SharedPublic entries before their
TTL expires, starting 20 seconds before the existing entry's expiry deadline.
Execute the background document regeneration in a bounded Worker-thread pool,
including CPU-intensive composition, HTML processing and representation preparation.
Scheduling an async callback on the HTTP event loop, or moving only edited Snippet
code to the existing pool, does not satisfy this requirement.

Keep refresh eligibility, freshness and result acceptance in the application layer.
Thread lifecycle, messages and execution are adapter responsibilities behind explicit
business-oriented ports, wired in composition. Domain, application and port contracts
must not expose Worker, MessagePort or thread-protocol types. Reuse the normal
application rendering behavior, including current authorization and published inputs,
without a second rendering implementation or direct cross-capability storage access.

TTLs of 20 seconds or less use ordinary blocking regeneration on a miss and no
background refresh. The page editor warns about this when a short TTL is entered.
Specify bounded trigger/admission rules in the refresh contract; do not introduce
immediate refresh loops.
Distinguish reduced visitor waiting from reduced generation CPU time.

Acceptance:

- Serve the current entry only while it is still valid. A failed refresh never
  extends its original deadline; expired entries retain the blocking-fill/error
  semantics. Do not introduce stale-on-error or stale-while-revalidate implicitly.
- Refresh through normal application rendering with current access checks,
  respecting every dependency's freshness limit and cache-bypass signal.
- Share work with concurrent fills and refreshes for the same key. The serving
  composition owns cache admission and result acceptance; worker-local memory
  cannot implicitly update the serving cache. Validate site/release/key and the
  current maintenance generation before accepting a completed document.
- Bound Worker count, active jobs, queue length/wait, memory, transfer bytes and
  aggregate CPU/database connection budgets, including any Snippet Workers used
  during refresh. Reserve foreground capacity; do not spawn a Worker per entry
  or admit all pages simultaneously without limits. Saturation must not silently
  move background regeneration onto the HTTP event loop.
- Measure concurrent foreground HTTP latency, errors and event-loop delay while
  many synthetic entries reach their refresh window together, including cache
  hits and misses. Worker isolation alone is not evidence against CPU starvation.
- Publication, maintenance and shutdown cancel or fence old work. Independent
  visitor disconnects retain correct cancellation behavior.
- Every background Promise has an observed outcome and cleanup path, including
  abort-before-admission, timeout, competing failures and late completion. Cover
  Worker startup failure, crash, message failure and termination; discard late
  replies and release reservations only when physical work settles.
- Define behavior across independent application processes; do not claim shared
  invalidation or coordination that is not implemented.

### 6. Create dumps in a separate operating-system process

The owner reports that creating a dump currently blocks the site. Move full-site
and partial dump creation out of the HTTP-serving process for CMS 0.12.0. An async
function in the same event loop does not provide this isolation. Keep orchestration
in application use cases and bind process execution through explicit ports/adapters;
do not introduce a separate business service or unrelated broker.

Acceptance:

- Public document delivery and ordinary administration reads remain responsive
  during capture, BSON/file serialization, checksumming and gzip compression.
  Measure concurrent public HTTP latency and event-loop delay during large
  synthetic full-site and partial exports, including HTML-cache misses.
- Specify job admission, identity, progress/status, completion/download and errors
  before implementation. Bound processes, queued work, memory, CPU and database
  connections; reject excess work explicitly instead of silently blocking HTTP.
- Replace the current process-local maintenance fence with an explicit
  cross-process contract. Preserve consistent database/filesystem capture, tenant
  isolation and exclusion of conflicting publication, writes and restoration.
  Isolation does not authorize taking an inconsistent snapshot.
- Preserve existing dump framing, schema validation, checksums, private storage,
  authorization and restore compatibility. Pass only validated job identities and
  settings to workers; keep credentials and private payloads out of logs and IPC.
- Observe spawn, IPC, stream and Promise failures. Cover cancellation before/during
  capture, timeout, worker crash, parent shutdown and late completion. Clean up
  temporary files and locks on each known outcome; reconcile uncertain outcomes
  without presenting a partial archive as Ready.
- Validate that a child process cannot bypass ownership/access checks or race a
  restore in another process. Use isolated fixtures for failure/concurrency tests.

The process and job lifecycle decision is recorded in ADR 0075 and the
[dump contract](site-dumps.md).

The owner canceled the Snippet/Chunk drawer workstream on 2026-11-10 after
clarifying that Chunks call Snippets. No tree or nested Chunk editor is required.

## Contracts and architecture

Before each implementation, record deliberate architecture changes in an ADR and
update affected ports/contracts. In particular, background refresh changes the
current foreground-only cache lifecycle. This release plan does not silently
replace that contract or authorize direct storage access from add-ons.

## Measurement and verification

Capture a fresh 0.11.0 baseline before implementation. Use synthetic fixtures in
the clean CMS; installation-specific evidence stays private in the site project.
Compare the homepage and a representative secondary Request page with identical
published content, equivalent assets, fixed settings and an unchanged dataset.

For every workstream, use interleaved before/after variants under equivalent
process, connection, Worker and instrumentation conditions. Report median and
p95, sample counts, errors, output equivalence, CPU/memory and relevant stage
timings. Nested and parallel spans must not be added as independent costs.

Separate warm HTML hits, forced HTML misses with warm plans/Workers, actual TTL
expiry after idle, and first process requests. A forced expiry does not reproduce
idle recovery. Include concurrent misses and refresh/foreground contention;
report observed fallback and cancellation outcomes. Do not promise a cumulative
latency reduction before measuring it.

Follow the repository test-first workflow for behavior changes. Run explicitly
selected application, adapter, composition and publication/restore regressions,
with relevant architecture, lint, typecheck and build checks. Review every new
feature for rejected Promise paths. Do not run the entire test suite by default.
Release verification must cover single-page/site publication, restore fencing,
foreign-site rejection, disabled add-ons, per-page limits and preserved query
normalization. A result with unexplained slowdown requires investigation before
claiming an improvement.
