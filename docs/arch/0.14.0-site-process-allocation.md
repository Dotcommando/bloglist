# CMS 0.14.0: Site CPU budgets and adaptive dump capture

Requested by the owner on 2026-11-13. Target release: **0.14.0**.
Status: implemented for 0.14.0; release publication is separate.

This document records the requested behavior and acceptance criteria, without
implementation progress tracking. See [ADR 0082](../adr/0082-site-process-allocation.md)
for the original decision and [ADR 0083](../adr/0083-fork-supervision-and-database-placement.md)
for the accepted 2026-11-14 fork/database-placement architecture.

## Settings / General

Show all sites connected to this CMS installation, the total visible logical CPU
count, the effective CPU budget available to the CMS, allocations per site and
the unallocated remainder. Identify sites by their name and registered domain.
Distinguish desired allocation from currently running serving processes,
including a process temporarily lent to dump capture and a failed replacement.

Include MongoDB as a separate installation-wide resource row alongside the
sites. The administrator must be able to change its CPU allocation visually,
see the effective value and any pending/failed application, without manually
editing Compose. This requirement was clarified by the owner on 2026-11-13.

An authorized installation administrator can distribute the available CPU budget
between sites here. This is installation-wide configuration even when opened
from a particular site's settings. Preserve existing site-specific settings and
their authorization; site access alone must not grant resource-management access.
Changes survive restart and are validated and applied by the backend.
Concurrent edits must not overallocate installation CPU quotas; serving-worker counts may exceed the CPU recommendation.

Site allocations use integer serving-process slots, separately from CPU quotas.
This does not itself pin a process to a physical core or reserve exclusive CPU
time. Display the distinction rather than promising hardware isolation that the
deployment does not enforce. Account for container CPU affinity and quota;
the host's advertised CPU count alone is not an allocation limit.
On Linux, read the process CPU affinity mask independently from the cgroup v1/v2
quota. Integer available-parallelism counts may already round a fractional quota:
a 1.5 CPU quota with two allowed CPUs remains 1.5 CPU, while affinity to one CPU
limits it to 1. Preserve a positive quota such as 0.1 CPU for recommendation and
dump-capacity calculations.

### Resource hierarchy in the interface

The owner's requested visualization uses an outer frame labelled **Docker**.
Inside it, place the database resource row first, then a nested frame labelled
**CMS processes (fork)**, containing the connected sites. Show the installation CPU
budget, the database quota and the aggregate CMS container quota with explicit
`CPU` units. Site rows show their integer serving-process allocation while the
selected implementation has no per-site CPU-quota enforcement.

Illustrative layout, assuming a configured 6.0 CPU installation budget and
temporarily omitting infrastructure headroom from the arithmetic:

```text
Docker                                        Budget: 6.0 CPU
  DB (MongoDB 8.0.34)                          Limit:  3.4 CPU
  CMS processes (fork) (CMS container)              Limit:  2.6 CPU
    domain1.com                               Processes: 1
    domain2.com                               Processes: 1
    domain3.com                               Processes: 1
```

This illustrates the distinction, not an approved process-count default or a
target MongoDB release. The three processes share the 2.6 CPU ceiling; they are
not individually guaranteed or limited to `1.0`, `1.0` and `0.6` CPU. The owner
explicitly excluded fractional per-site CPU quotas from 0.14.0; do not add per-site
CPU inputs or cgroup enforcement for them. Do not display fractional process
counts or relabel process counts as enforced CPU limits.

The DB label uses the observed database engine name/version, not a hardcoded
example. Keep image identity/tag and engine version distinguishable in details;
an existing `8.0.34-noble` image tag must not be confused with a MongoDB server
version suffix or silently rewritten in observed deployment information.
Display desired/effective limits, running-process counts and apply errors.
If showing utilization, label it as measured usage with its sampling interval,
separately from configured limits; an allocation diagram alone is not live load.

Include supervisor, proxy, executor, host/VM overhead and dump/refresh work in
the real capacity policy; `6.0 - 3.4 = 2.6` alone does not reserve headroom for
those consumers. The outer Docker frame describes managed resources, not an
assumption that Docker automatically has one shared 6.0 CPU quota.

Docker's fractional quota does not round the container into a machine with that
many integer CPUs. On Linux, the pinned Node.js/libuv parallelism query uses CPU
affinity; it can still report six available logical CPUs with a 2.6 CPU-time quota
and no narrower affinity. Read/verify the actual quota and affinity through the
deployment control boundary rather than deriving capacity from that integer.

### Recommended worker count without a hard cap

The owner accepted this policy on 2026-11-13: recommend
`ceil(effectiveCmsCpuBudget)` for the installation's total serving-worker count,
but impose no hard cap derived from that recommendation. Prefer keeping the
number of sites within the available CPU capacity, without rejecting additional
sites or worker allocations solely because they exceed the recommendation.
For example, 2.6 CPU suggests three serving workers; 0.6 CPU suggests one.
The actual CPU ceiling remains fractional and enforced by Docker.

This count is installation-wide, not a fresh allowance for every site. Display
the recommendation beside desired/running worker and site counts. Exceeding it
shows a non-blocking explanation of shared CPU time, memory and connection costs;
it does not disable Save, require a separate override/confirmation or prevent
adding a site. Keep CPU-quota validation: allowing extra workers does not enlarge the Docker CPU
ceiling. No estimated memory/connection budget determines a maximum worker count.
Extra processes do not create extra CPU, and asynchronous I/O does not require a
new worker for every waiting request. Do not introduce a shared site pool merely
to force compliance with this recommendation.

The resource model accounts for dump children as well as serving workers using
the owner's final rules below. Count the supervisor separately from serving workers while retaining
its CPU/memory cost in the common container budget. Reconcile this with the
accepted borrowed-slot and in-process dump branches. A changed recommendation
alone must not automatically stop existing workers or sites. Background threads
remain bounded separately; the recommendation is not a total OS process/thread
limit.

### Live CPU-load graphs

Begin sampling and supplying graph data every **one second from successful
administration login**, independent of whether Settings / General is open.
Immediately show the observed logical CPU count; use a separate graph for each
CPU, labelled CPU 0, CPU 1, etc., with an individual 0-100% scale and a common
time axis. The first usage interval needs a baseline and a subsequent sample;
do not fabricate a pre-login point. Show these graphs in the separate
Settings / CPU usage submenu tab. Only the browser retains the bounded visible
chart points received during its current connection; the server stores no metric
history and provides no historical replay.
Support inspection of each CPU without relying on color alone. Identify the
source as host or Docker Linux VM/WSL; VM CPUs must not be labelled as physical
Windows cores.

Collect per-CPU cumulative OS counters through an explicit read-only metrics port
and trusted local adapter/helper, and calculate usage from successive samples.
Do not derive measured load from assigned quotas, worker counts, request counts
or the integer parallelism query. A per-CPU graph shows the observed host/VM load,
including workloads outside this CMS; it is not a per-site attribution graph.
Keep container-level CMS/MongoDB usage and quota values separate from those
per-CPU percentages if displayed alongside them. `1.0 CPU` of aggregate usage
means one CPU equivalent, not 1% of the entire host or necessarily one pinned CPU.

Stream the current sample once per second through an authenticated WebSocket
opened after administration login. This is a narrow read-only administrative
telemetry transport; site/business operations remain REST/JSON. Validate trusted
Host/Origin and the active administrator session, including session expiry while
connected. Do not expose Docker control or command execution through the socket.

The owner explicitly excludes server-side metric storage, including an in-memory
history/replay buffer, database records, files and metric logging. Keep only the
previous cumulative counters/time needed to calculate the next interval, the
current sample and bounded transport state; discard them when collection stops.
Use one shared collector while at least one authorized admin client is connected.
Navigating between admin sections keeps that connection/collection alive.
Logout, session expiry, disconnect or a detected dead connection removes the
subscriber. When the last subscriber leaves, stop the sampler and release its
timers/resources. No connected admin means no CPU-metric collection.

Reconnection starts with current counters and a fresh baseline, without replay.
Background suspension or a slow receiver must not create a metric backlog;
bound send buffers, skip unsendable samples/close stalled connections and show
gaps rather than accumulating history. Keep collection/streaming independent of
a site-serving event loop that may stall, or mark delayed samples unavailable.

Only authorized installation administrators may read installation-level metrics.
Expose a restricted metrics response rather than a public/raw host or Docker
API. Missing permissions, unsupported sources, resets, CPU topology changes and
lost samples produce a clear unavailable/gap state, not fabricated zeros or
stale data presented as live. Use monotonic elapsed time for rates and UTC
instants for sample timestamps; display time in the configured IANA zone.

Resource saves show a circular overlay within the visible form while applying,
then show the saved and ready process counts or an explicit failure beside Save.
Background refresh has separate loading state and must not disable editable
controls. Ignore an obsolete read after a save, and retain edits made while a
read was pending. A save timeout releases global busy state before a bounded
actual-state read; confirm success only when saved/running values match the
request. An unchanged successfully applied form normally has Save disabled.

## Explicit database placement

`ZARYA_DATABASE_PLACEMENT` is required: `ManagedLocal`, `UnmanagedLocal` or
`Remote`. Never infer it from the connection URI. ManagedLocal uses the restricted
helper to apply separate MongoDB/CMS quotas. UnmanagedLocal requires the explicit
`ZARYA_CMS_CPU_BUDGET` and does not control/subtract an invented database quota.
Remote deducts no database CPU from the application machine. An optional explicit
CMS budget is bounded by its available CPU quota/affinity. The infrastructure
reserve remains explicit. A placement change preserves saved site process counts
and resets only the applicable database-budget accounting.

The coordinator, its threads, site processes and dump children share the CMS
budget; no whole CPU is reserved for the coordinator. The per-process MongoDB
pool setting `ZARYA_MONGO_MAX_POOL_SIZE` defaults to 5; capture retains its separate
two-connection pool. Monitoring connections are additional. Neither these pool
sizes nor RAM estimates impose a maximum serving-process count.

## CMS process model

Use CMS-owned process supervision without PM2. One backend installation serves
multiple sites with site-specific serving process allocations. This does not
create separate backend deployments or business microservices. Route requests
using validated site identity into the assigned site's process pool; ordinary
round-robin across all workers does not enforce the requested distribution.

Changing allocation drains affected processes before stopping them and admits
replacement processes only after successful initialization. Keep trusted Host
resolution, authentication, site isolation and publication visibility intact.
Report an apply/startup failure truthfully instead of claiming the desired
allocation is running. The coordinator directly forks serving and capture workers. Site workers delegate
child capture over private IPC; their maintenance/operation ownership is distinct
from the capture child's actual parent. Report actual startup failures, and keep
container memory and per-process connection-pool settings separate from worker
allocation. Do not compute a process cap from memory estimates or connection totals.

The coordinator owns a keep-alive HTTP agent for private worker requests and
releases it at shutdown. Connection-specific headers, including those named by
`Connection`, stay within their own network hop; a worker closing its connection
does not force the public client to reconnect. Verify bounded connection counts
under repeated concurrent traffic, worker disconnects and independent site ports.
A transient background session-check failure preserves the mounted admin workspace
and unsaved values, with a visible retry action and automatic retry after five
seconds. Only an authentication rejection (HTTP 401) switches to the sign-in view.
Initial session verification still gates entry to the workspace.

Existing cache-refresh Worker threads, native library work and control-plane
activity also consume CPU. The capacity model must include their bounded
concurrency; a serving-process count is not the total thread count.

## Dump execution policy

From 0.16.0, apply the following order to site, category and installation dump creation:

| Capacity at admission | Required behavior |
| --- | --- |
| The target site has at least two serving processes | First drain and stop one process belonging to that site, then create a dump child in its place. Keep the remaining site processes serving. After capture, child exit and cleanup, start a replacement serving process. This branch takes priority even when spare CPU budget exists. |
| The target site has one serving process | Create the dump inside that site's serving process. Event-loop stalls and delayed responses are accepted. Do not create an additional dump process. |

Do not borrow another site's allocation or a CPU reserved for the database or
other infrastructure. Stop the selected serving process only
after it has drained; confirm exit before starting the dump child. The supervisor
must recognize this intentional stop and avoid immediately respawning it.

The initiating request must remain owned by a surviving process or supervisor
when a serving process is retired. Preserve the existing pending request/busy
state, completed metadata result and archive-list reconciliation after a lost
response. No new job catalogue, automatic retries or queue is requested.

Return borrowed capacity on success, failure, cancellation, spawn/IPC failure
and timeout. Do not start the replacement while a dump child still occupies the
slot. A failed replacement is a visible degraded allocation, not a successful
return to normal capacity. Recovery after a supervisor crash must reconcile
leases, live processes and temporary capacity before admitting new work.

In-process capture must reuse the existing archive implementation and preserve
staging, validation, atomic completion, cleanup and error results. It has no
child PID/IPC lifecycle or independent child heap/pool. Timers and cancellation
cannot preempt synchronous JavaScript while its event loop is blocked; do not
promise the child-process hard-stop behavior in this mode.

## Shared correctness boundaries

ADR 0075 and the current dump contract assume one HTTP writer. Multiple serving
processes require coordinated admission and draining across **all** processes,
including hook mutations and Snippet commands. Preserve snapshot consistency,
the installation-wide dump/restore lock, read-only creation admission and
exclusive restoration. Never introduce independent per-process maintenance gates
that leave another writer active during capture.

Publication activation and media/source mutations must remain coherent across
processes. Fence stale cache work and propagate invalidation to every affected
process. Existing background jobs must not execute once per serving process
merely because composition was duplicated. Preserve add-on ownership and avoid
loading site business packages into the clean CMS distribution for verification.

## Docker and MongoDB boundary

MongoDB CPU enforcement belongs to Docker/host configuration, controlled through
the requested administrative interface. Compose can set
`mongo.cpus: 1.0` to cap aggregate CPU time at one CPU equivalent, or
`mongo.cpuset: '0'` to restrict execution to one logical CPU. Neither setting alone
excludes other workloads from that CPU. Strict separation requires corresponding
non-overlapping CMS/other-workload affinity and host-level configuration.

MongoDB is shared by sites; these controls apply to its container, not individual
sites' queries. MongoDB can use multiple cores, so a one-CPU cap can become a
bottleneck even when the CMS has more serving processes. Do not assume one CPU
is the appropriate production database allocation.

On Docker Desktop the relevant CPUs belong to its Linux VM/WSL environment;
their numbering must not be presented as guaranteed physical Windows core IDs.
Show the effective CMS limit and any explicitly configured infrastructure budget;
do not infer the database's reservation from what the CMS container can see.
Production preparation writes database/CMS CPU quotas to a private Compose
override. Native/local environments expose unmanaged quota control explicitly.

For 0.14.0, include changing the managed MongoDB container's CPU limit through
Settings / General. Fractional CPU equivalents such as `0.8` and `1.2` are valid
Docker quotas: they limit aggregate CPU time across the container's threads,
not physical fractions of a core. A single JavaScript execution thread still
cannot execute on 1.2 CPUs simultaneously. Keep serving-process counts integral
and separate from fractional container quotas in both contracts and labels.

The UI change must reach a real enforcement boundary; saving a number in MongoDB
alone is insufficient. Docker supports updating CPU quota/affinity on a running
Linux container. Verify the applied setting and persist the intended deployment
configuration so container recreation does not silently revert it. Desired and
observed values must remain distinguishable after a partial/uncertain failure.

Proposed integration: an explicitly configured local resource-control adapter
through a narrowly scoped privileged helper, permitted to inspect/update only
the installation's registered containers and CPU settings. Keep unrestricted
Docker socket/daemon access out of the HTTP-serving CMS. The exact helper
protocol, authorization and deployment binding require agreement before code.
This is a technical deployment control boundary, not a business microservice.
External/unmanaged MongoDB and deployments without this capability must display
an explicit unavailable/read-only state rather than pretend to apply the value.

Validate MongoDB changes against the same installation capacity policy as site
allocations; never advertise a CPU quota as a guaranteed reservation. Coordinate
reductions with serving/dump capacity and concurrent edits without silently
overcommitting or rewriting site allocations. Quota enforcement and strict
exclusive affinity remain different modes; finalize supported modes before code.

## Local multi-site load verification

The owner explicitly requested local load testing for 0.14.0, with a second site
alongside the existing local site installation and visual inspection of cluster
distribution. The principal acceptance goal is **enforcement of each site's
configured process count and isolation of its serving event-loop freezes from
other sites**, not cosmetically equal CPU graphs. Prepare the additional
synthetic site in the separate site project
or an isolated installation copy, not as content seeded into the clean CMS.
Keep its data/publications/storage scoped separately and preserve the existing
site. Do not direct the workload at production or external business services.

No hosts-file edit is necessary. The current ResolveSite operation looks up the
registered serving authority, including its port. Illustrative local addresses
are `http://localhost:3000` and `http://localhost:3002`, registered to different
site identities. These are examples; use available configured ports. Two site
addresses do not by themselves start a second listener. Reach the **same** CMS
installation/cluster using explicit Docker port publishing to one internal HTTP
listener or a loopback-only proxy that preserves the registered Host authority.
Do not start two independent CMS backends and call that cluster balancing.
For request-only generators, an explicitly registered Host authority or a
client-local DNS override can also avoid hosts-file changes; preserve normal
site resolution and unknown-authority rejection.

After the cluster/resource/metrics features exist, run bounded reproducible local
workloads against real published Request routes, with controlled comparable
content and no live/paid loaders. Record baseline, warm-up and steady-state
intervals and distinguish cache hits from actual rendering. Use concurrent
connections and record keep-alive behavior: cluster connection distribution is
not a guarantee of equal requests, equal CPU time or equal instantaneous core
load. A hot static/cache-hit workload alone does not demonstrate rendering
parallelism, and equal per-core graphs alone do not prove per-worker balancing.

Record per-site/per-worker request counts, worker identity and CPU-time deltas
through private test diagnostics, plus throughput, latency percentiles and error
counts. Avoid public diagnostic headers/identities or a fake production route.
Use the admin's real one-second per-CPU graphs for the owner's visual review,
while correlating them with worker metrics. Pin the generator to separate
resources or account explicitly for its consumption on the same machine; host
graphs otherwise include the generator and MongoDB as well as CMS workers.

Use separate assigned serving-worker pools. Exercise a site A with one serving
process and a site B with two or more, then swap allocations. Inject bounded,
deterministic synchronous work through isolated published rendering fixtures to
block A's serving event loop while requests continue to B. Demonstrate that B's
own workers continue admitting/completing requests and the supervisor/telemetry
remain responsive. A's requests must not be moved into B's processes as fallback,
and the supervisor must not create extra A workers beyond its configured count.
Check the same ownership/count rules during resizing, worker replacement and
temporary dump-slot lending. Account for planned transitions explicitly rather
than counting a retiring worker as an unreported additional allocation.

Measure B's latency/errors before, during and after A's freeze with controlled
CPU/DB/memory headroom and an agreed tolerance. Separately exercise shared-resource
saturation and report its effects. A site's process-count budget is not a hard
per-site CPU/RAM/DB reservation: all workers still share the CMS container limit
and database/storage. Process isolation prevents a common JavaScript event-loop
freeze, but cannot promise unchanged neighboring latency under shared-resource
exhaustion. Do not claim stronger isolation or introduce excluded per-site CPU
quotas. Dump write gates intentionally remain installation-wide under the agreed
snapshot contract; their expected write blocking is distinct from a leaked freeze.

Cover comparable traffic to equal worker pools, changed process allocations,
unequal traffic to the two sites, and dump creation under load through the three
accepted execution branches. Check site isolation, continued serving, returned
capacity, metric continuity/gaps and absence of lost/unhandled failures. Define
workload, duration and balancing tolerance before measurements; do not claim
perfect equality from round-robin or promise a percentage without observations.
Record actual environment/quotas, commands and results in a focused audit report.
Observed results are recorded in the [focused audit](../audits/0.14.0-site-process-allocation.md). Automated test listeners
must close; the owner starts any persistent local application from the IDE.

## Owner-approved defaults and examples

Historical implementation notes from 2026-11-13. For current dump execution, see [the policy above](#dump-execution-policy).

- Start with one CPU of database budget and one process for each site. With at
  least two available CPUs, leave the remaining capacity unallocated. A new site
  still receives one process when this exceeds the recommendation; explain
  shared resources without requiring an override. Zero site processes are invalid.
- On a one-CPU installation, MongoDB and the site's process share that CPU.
  There is no distributable capacity and allocation controls are disabled.
  With one site and two CPUs, the one-CPU database/one-process site distribution
  also has no editable allocation and its dump runs inside the serving process.
- On three CPUs with one site, allocate one CPU to MongoDB and one site process;
  leave one CPU free. Its dump uses a separate process.
- On six CPUs, MongoDB at 2.4 CPU and site pools of one and two processes leave
  0.6 CPU free. The two-process site always lends one of its own processes; the
  one-process site uses a new child against the positive 0.6 CPU remainder.
- With MongoDB at 3 CPU and the same pools on six CPUs, the two-process site
  still lends a process; the one-process site captures in its serving process.
- Under the resource form, describe the selected site's actual dump mode and
  expected availability from the current allocation. Explain separate capture,
  lending with remaining workers, or a temporary serving-event-loop stall.
  Avoid generic advice that contradicts the displayed user's situation.
- CPU-time quotas are not affinity or exclusive hardware reservations. A positive
  fractional remainder permits a child without promising unchanged latency.
- Document these rules in both README.md and README.ru.md after implementation.

The Docker helper is a restricted local deployment-control service reached over
a private Unix-domain socket; it is separate from the CMS process supervisor.
It may inspect/update CPU settings only for registered installation containers.
Persist deployment configuration and reconcile desired versus observed limits.
The supervisor coordinates process ownership, routing and write admission.

Approved telemetry defaults: 300 points per CPU in browser memory; one-second
samples, heartbeat every 15 seconds, dead-client expiry after 45 seconds, no
missed-sample queue. Freeze verification uses a 30-second warm-up, 120-second
measurement and bounded five-second blocking work. With verified shared-resource
headroom, neighboring requests have no errors and their p95 increase is at most
the greater of 20% of baseline or 20 ms. Report saturation separately.

## Contract implementation details

Preserve archive status and existing delivery/administration semantics when
assigning defaults to existing sites. The supervisor is counted separately from
site processes, with its cost inside the shared CMS quota rather than an invented
additional exclusive CPU reservation. A lower capacity recommendation does not
silently rewrite desired site allocations. The no-hard-cap decision is settled, and
fractional per-site quotas are excluded. Live telemetry uses one-second samples
only while authorized admin clients are connected, without server-side history.
Record encoded transport bounds and source capabilities in
`docs/arch/transport-limits.md` at implementation. Resource reads distinguish
desired and observed state and expose apply failure. Updates use an expected
configuration version to reject stale edits. Uncertain Docker acknowledgements
require observed-state reconciliation, never an invented successful result.
Coordinator loss closes new write admission until consistency is recovered.
The UI uses 0.1 CPU precision for managed database quotas.
