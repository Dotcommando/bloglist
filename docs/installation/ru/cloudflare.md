# Доставка в Cloudflare

[Установка](INSTALLATION.md) · [English](../en/cloudflare.md)

Укажите `CLOUDFLARE_ACCOUNT_ID` и `CLOUDFLARE_API_TOKEN` в приватном `.env`.
Ограничьте токен нужным аккаунтом/зоной, предоставив права загрузки Worker/статики
и Custom Domain/маршрутов, необходимые Wrangler. Исполнитель также читает деплои
Worker и список Worker-доменов аккаунта для подтверждения доставки. Если у токена
есть фильтр клиентских IP, разрешите исходящие адреса исполнителя.
HTTP-процесс не получает реквизиты провайдера.

Скопируйте `cloudflare.example.json` в приватный `cloudflare.json`. Укажите ID
опубликованного сайта, постоянное имя Worker, выбранный публичный origin и доступный
backend origin. Задайте одинаковый случайный `ZARYA_EDGE_PROXY_SECRET` для backend
и исполнителя. Исполнитель передаёт его в секреты Worker временным приватным файлом.

```sh
docker compose run --rm --no-deps cloudflare node /app/dist/deployment.js configure
docker compose --profile cloudflare up -d cloudflare
docker compose run --rm --no-deps cloudflare node /app/dist/deployment.js status
```

Обычный запуск HTTP-приложения не создаёт Worker. Его создаёт первая успешная
загрузка исполнителя после публикации сайта и настройки включённой цели доставки.
Нужны непустые реквизиты Cloudflare с необходимыми правами; одна запись DNS
не запускает доставку.

Настройка ставит текущую публикацию в очередь. Последующие зафиксированные активации,
включая изменения только маршрутов, обрабатываются автоматически. Сохранение черновика
не запускает загрузку. У цели может выполняться одна сохранённая попытка; новые
публикации ожидают её завершения. Перезапуск сохраняет состояние доставки.

Администратор также может настроить цель на вкладке **Настройки / Деплой**
выбранного сайта. Укажите выбранный публичный адрес сайта и отдельный доступный
адрес сервера. Вкладка показывает активную публикацию CMS отдельно от последней
подтверждённой доставки, попытки, безопасную диагностику и повтор с проверкой
версии. Кнопка проверки проверяет файлы публикации и доступность сервера;
реквизиты провайдера и принадлежность домена проверяет исполнитель.
Реквизиты остаются в его приватном окружении. Обновление читает сохранённый
статус без загрузки сайта.

`Succeeded` требует активной версии провайдера, правильного Custom Domain и публичного
ответа с меткой конкретной попытки/публикации. Подготовка файлов, неуспешный или
неопределённый выход Wrangler не подтверждают публичную доставку. В `Failed` хранится
безопасная диагностика; устраните причину перед явным повтором:

```sh
docker compose run --rm --no-deps cloudflare node /app/dist/deployment.js retry
```

`OutcomeUnknown` блокирует следующую загрузку. Согласование проверяет провайдера
и публичную метку без повторной загрузки. Не сбрасывайте это состояние и не удаляйте
файловые блокировки, пока старый процесс может работать. Если результат установить
не удалось, изучите историю провайдера и разрешите прерванную операцию до продолжения.

Для явной проверки без загрузки или ручного обслуживания:

```sh
docker compose stop cloudflare
docker compose run --rm --no-deps cloudflare node /app/dist/prepare-cloudflare.js --deploy --dry-run
```

Без `--dry-run` команда загружает сайт вручную. Сначала остановите автоматическую
доставку, завершите текущие операции и проверьте публичное состояние перед её
возобновлением. Приватный workspace исполнителя нельзя раздавать как статику или
публиковать вместе с резервными копиями. Только `deploy/public/` содержит публикуемые файлы.
