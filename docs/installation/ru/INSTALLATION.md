# Установка на сервер

[English](../en/INSTALLATION.md)

Используйте отдельную установку сайта. Её данные, приватные настройки и бизнес-аддоны
хранятся вне чистого репозитория CMS. Руководство относится к поставляемому
`compose.production.yml`: HTTP-приложение, MongoDB с аутентификацией и replica set,
Caddy и отдельный исполнитель Cloudflare. Нужны Docker и Docker Compose на Linux;
версии образов и Node/npm закреплены в репозитории.

## Новая установка

Выполняйте команды из каталога установки. Выберите разные публичный и серверный
HTTPS-адреса. DNS backend должен указывать на этот сервер; откройте 80 и 443.
Публичный hostname будет принадлежать Worker. См. [домены и TLS](tls.md).

Запустите установщик интерактивно от root, заменив примеры своими зарегистрированными доменами:

```sh
bash scripts/install-production.sh https://www.example.test https://api.example.test
```

Установщик создаёт приватные настройки и защищённый replica set MongoDB, собирает образы, применяет и проверяет миграции, запрашивает администратора и запускает приложение и прокси. Он отказывается работать при существующих настройках, каталогах установки, стандартном проекте Compose или томе MongoDB. При ошибке изучите созданное состояние и используйте процедуру обновления или восстановления; не запускайте установщик повторно вслепую.

Скрипт администратора запрашивает email интерактивно и скрывает пароль. Скрипт
инициализации MongoDB создаёт ограниченную учётную запись приложения только при
пустом томе базы. Не запускайте начальную инициализацию поверх существующей установки.

Сначала открывайте `/admin/` по адресу backend: это исходный канонический адрес
администрирования. Создайте сайт, выберите его публичный адрес, установите и отдельно
включите нужные аддоны, затем опубликуйте сайт. Сохранение черновика не публикует.
Настройте доставку по [главе Cloudflare](cloudflare.md).

## Закрытые репозитории аддонов GitHub

Установите GitHub App в аккаунте владельца репозиториев аддонов. Выберите нужные
репозитории и выдайте право Contents на чтение. В приватном окружении процесса
CMS укажите `ZARYA_GITHUB_APP_CLIENT_ID` и `ZARYA_GITHUB_APP_KEYS_DIR`. Второе
значение — абсолютный путь к каталогу файлов PEM, доступный для чтения службе
CMS. Храните каталог вне исходников и публичных файлов. Zarya определяет ID
установки приложения по каждому закрытому репозиторию. Открытые репозитории
работают и без этих настроек.

При запуске без Docker задайте `ZARYA_GITHUB_APP_KEYS_DIR` абсолютным путём на
компьютере. Для Docker укажите Client ID в `.env`, положите PEM в
`.secrets/github-app` и выполните штатную подготовку
`node scripts/prepare-compose.mjs`. Скрипт подключит поставляемый Compose-файл
для локальной или production-конфигурации. Каталог монтируется только для чтения
в контейнер `app` по пути `/run/secrets/github-app`. Другой каталог на хосте можно
задать через `ZARYA_GITHUB_APP_HOST_KEYS_DIR` в `.env` до подготовки.

На Linux-проде подготовка от root даёт группе службы (GID 1000) доступ
на чтение стандартного каталога и имеющихся PEM. Для своего каталога задайте
права чтения для службы. Храните ключи вне Git, публичных каталогов и образа.
При замене положите полный новый PEM в тот же каталог с правом чтения для CMS.
Если файл скопировался с более строгими правами, штатная подготовка от root
исправит их в стандартном каталоге. Проверьте закрытый репозиторий, затем
отзовите старый ключ в GitHub. Имя файла и настройки при замене менять не нужно.

## Перенос существующей установки и обновление

Сохраняйте базу, `data/`, `sites/`, артефакты публикаций, дампы, runtime/секреты
установленных аддонов и приватное окружение. Код, черновики, активная публикация CMS
и доставленное во внешнюю систему содержимое являются разными состояниями.
Обновление кода или Git push сами по себе не доставляют содержимое сайта.

Cookie сессии привязана к сохранённой версии настроек установки. В резервной
копии базы всей установки сохраняйте installation_settings вместе с admin_users
и admin_auth_sessions; не пересоздавайте настройки при обычных обновлениях.
Смена адреса админки меняет версию и требует повторного входа.

Перед резервным копированием/восстановлением остановите исполнитель. Завершите или
согласуйте неопределённую загрузку провайдера. Для согласованного снимка BSON и файлов
остановите HTTP-записи; MongoDB оставьте работающей. Передавайте данные по защищённому
каналу, сверяйте хеши файлов, отпечатки базы, валидаторы и индексы. Сохраняйте исходную
установку до успешной проверки. Не перезаписывайте непустое назначение.

Перенесите одобренную версию CMS файлами, сохраняя настройки и содержимое установки.
Пересоберите образы приложения и исполнителя, примените и проверьте только новые
версионированные миграции, затем пересоздайте HTTP-приложение и исполнитель.
Не заменяйте применённый baseline и не используйте `docker compose down -v` при обновлении.

```sh
docker compose stop cloudflare app
install -d -m 0700 -o 1000 -g 1000 dumps/production/.coordination
node scripts/prepare-compose.mjs
chown -R 1000:1000 .secrets/resources
docker compose build app cloudflare
node scripts/release-consistency.mjs --image "cms-zarya-app:$(node -p "require('./package.json').version")"
node scripts/release-consistency.mjs --image "cms-zarya-cloudflare:$(node -p "require('./package.json').version")"
docker compose run --rm --no-deps app node dist/migrate.js
docker compose run --rm --no-deps app node dist/migrate.js --verify
docker compose --profile cloudflare up -d --wait app proxy cloudflare
```

Для команд исходников используется закреплённая версия Node.js. Если имена
образов изменены, подставьте свои имена приложения и executor. Подготовка берёт
тег из корневого package.json, сохраняет существующие квоты и приватные настройки.
Общий CPU-бюджет задаётся через `ZARYA_INSTALLATION_CPU_BUDGET`, резерв остальных
служб — через `ZARYA_INFRASTRUCTURE_CPU_RESERVE`. При первом запуске подготовки
в контейнере Node явно передайте общий бюджет: Docker CLI внутри него отсутствует.
Проверяйте фактические версии обоих образов до миграций. Сохраняйте каталог
`.secrets/resources` с ключом и Compose override при обновлениях и в резервных
копиях. Только отдельная локальная служба helper получает Docker-сокет;
обслуживающие процессы используют закрытый Unix-сокет. См.
[принцип распределения](../../../README.ru.md).

Production Compose явно задаёт `ZARYA_DATABASE_PLACEMENT=ManagedLocal`.
Для отдельно управляемой локальной БД выберите `UnmanagedLocal` и задайте
`ZARYA_CMS_CPU_BUDGET`; для БД на другой машине — `Remote`. В этих вариантах
нужно переопределить адрес MongoDB и зависимости сервисов; управляемый helper
для БД не запускается и не подключается к CMS. Размещение не выводится из URI.
CPU внешней БД не вычитаются из бюджета машины приложения.
`ZARYA_MONGO_MAX_POOL_SIZE` задаёт пул каждого обычного процесса (по умолчанию 5),
пул дампа остаётся отдельным, до двух соединений. Число процессов сайтов
не ограничивается расчётами RAM или соединений. Общие лимиты контейнера
настраиваются при развёртывании. См.
[ADR 0083](../../adr/0083-fork-supervision-and-database-placement.md).

Для смены основной версии MongoDB нужен отдельный
[порядок обновления](../../arch/mongodb-9-upgrade.md), проверенная независимая
резервная копия и окно обслуживания. Обновление исходников приложения не означает
автоматической замены образа существующей базы.

Восстанавливайте согласованные копии базы и файлов вместе при остановленном
исполнителе. CMS также блокирует восстановление сайта при идущей или
неподтверждённой внешней доставке через общий приватный каталог
dumps/production/.coordination. Исполнитель получает запись только в этот
подкаталог, архивы остаются read-only. Сначала согласуйте неизвестный результат
провайдера; не удаляйте служебные файлы для обхода защиты. Проверьте выбранную
публикацию и установленный Worker по текущему контракту доставки.
Историю деплоев провайдера сохраняйте отдельно от резервных копий CMS.
См. [диагностику](troubleshooting.md).

## Проверенные артефакты исходников

Используйте версионированный архив исходников с отдельной SHA-256. Проверьте
контрольную сумму архива и перечень распакованных файлов в пустом временном каталоге
до переноса кода в установку. См. [команды и формат артефакта](../../arch/release-artifacts.md).
Сохраните .env и все данные сайта. Пересоберите оба образа текущего выбранного
релиза, примените и проверьте ожидающие миграции без изменения прежних записей.
Нажмите версию в шапке админки,
чтобы увидеть коммит и контрольную сумму файлов установленной сборки.

## Резервная копия и восстановление установки

Выполняйте команды Linux от root из каталога установки с доступом к Docker. Остановите
исполнитель, дождитесь завершения загрузки и согласуйте неизвестный результат
провайдера. Остановите HTTP-приложение, оставив MongoDB работающей. Копия включает
черновики, публикации, приватные настройки, медиа, дампы и пакеты/секреты аддонов
в `dumps/production/.installed-addons`:

```sh
set -eu
umask 077
backup_dir="backups/$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$backup_dir"
docker compose stop cloudflare app proxy
docker compose exec -T mongo sh -c 'exec mongodump --username "$MONGO_INITDB_ROOT_USERNAME" --password "$MONGO_INITDB_ROOT_PASSWORD" --authenticationDatabase admin --db "$MONGO_APP_DATABASE" --archive --gzip' > "$backup_dir/database.archive.gz"
tar -czpf "$backup_dir/installation.tar.gz" .env .secrets cloudflare.json .cloudflare data sites artifacts/production dumps/production
docker run --rm -v cms-zarya_caddy-data:/data:ro -v "$PWD/$backup_dir:/backup" node:26.7.0-bookworm-slim tar -czpf /backup/caddy.tar.gz -C /data .
(cd "$backup_dir" && sha256sum database.archive.gz installation.tar.gz caddy.tar.gz > SHA256SUMS)
```

Имя тома Caddy соответствует поставляемому имени проекта Compose `cms-zarya`;
при его переопределении проверьте `docker volume ls`. Храните копию сертификатов
и ACME-аккаунта приватно. Проверьте коды завершения команд и перенесите копию
в защищённое хранилище другой машины. Возобновляйте app/исполнитель только после
успешного снимка; сохраните соответствующую ревизию CMS и образы.

Восстанавливайте в отдельный пустой каталог установки с той же ревизией CMS.
Проверьте `sha256sum -c SHA256SUMS` в каталоге копии и распакуйте архив командой
`tar -xzpf /absolute/backup/installation.tar.gz` из пустого каталога установки.
Не распаковывайте поверх действующей установки. Восстановленный `.env` выбирает
production-файл Compose. Задайте в нём новое свободное `COMPOSE_PROJECT_NAME`
и экспортируйте то же значение в оболочке; сначала проверьте существующие проекты
и тома. Это исключает случайное использование томов исходной установки.
До запуска прокси восстановите Caddy в новый том этого проекта:

```sh
docker volume create "${COMPOSE_PROJECT_NAME}_caddy-data"
docker run --rm -v "${COMPOSE_PROJECT_NAME}_caddy-data:/data" -v /absolute/backup:/backup:ro node:26.7.0-bookworm-slim tar -xzpf /backup/caddy.tar.gz -C /data
```

Запустите MongoDB с новым пустым томом базы этого проекта, дождитесь инициализации
и восстановите BSON:

```sh
docker compose up -d --wait mongo
docker compose exec -T mongo sh -c 'exec mongorestore --username "$MONGO_INITDB_ROOT_USERNAME" --password "$MONGO_INITDB_ROOT_PASSWORD" --authenticationDatabase admin --archive --gzip' < /absolute/backup/database.archive.gz
docker compose build app cloudflare
docker compose run --rm --no-deps app node dist/migrate.js --verify
```

Дамп не включает глобальных пользователей базы admin; инициализация новой MongoDB
создаёт прикладную учётную запись из восстановленных настроек. Оставьте HTTP-запись
и исполнитель остановленными до проверки базы и файлов. Сначала запустите app
и proxy, проверьте админку и активную публикацию, затем согласуйте состояние
провайдера перед запуском исполнителя. Копия CMS не восстанавливает и не
откатывает публичный деплой Cloudflare.
