# Тестовый сайт Bloglist

[Локальная установка Bloglist и релиз аддона](docs/bloglist-trial-catalog.md)

[English version](README.md)

Этот репозиторий содержит локальный сайт Bloglist на CMS Zarya. Сайт использует
опубликованный аддон Bloglist через реестр CMS. Исходники CMS и аддона находятся
в отдельных репозиториях согласно [ADR 0037](docs/adr/0037-clean-cms-and-site-installations.md).

Ядро поддерживает сайты, страницы, независимые URL, редактируемые шаблоны,
чанки и сниппеты, медиа, предпросмотр черновиков, неизменяемые публикации,
публичную выдачу, учётные записи администраторов и подключения аддонов к сайтам.
Локальными данными сайта и установленными пакетами управляет CMS.
Версионируемый SDK расширений находится в `packages/addon-contracts`.

Серверный API объекта `cms` доступен доверенным сниппетам и аддонам.
Руководства разработчика: [на русском](docs/guide/ru/README.md) и
[на английском](docs/guide/en/README.md). Границы и поведение API описаны
в [контракте реализации](docs/arch/system-object-api.md).

Независимый проект katerina-bloom содержит свою установку, аддон событий,
резервные копии исходников, медиа, публикации и приватные настройки. Сам аддон
разрабатывается отдельно в zarya-addon-events. Эти проекты не являются
runtime-зависимостями и источниками импортов для данного репозитория CMS.

[История изменений](CHANGLOG.ru.md).

## Локальная разработка

Используйте Node.js 26.7.0 и npm 11.19.0. Версии зависимостей закреплены,
`package-lock.json` хранится в репозитории. Скопируйте `.env.example` в приватный
`.env` и укажите базу, каталоги хранения и доверенного локального оператора.

```sh
npm ci
node scripts/prepare-compose.mjs
docker compose up -d --wait mongo
npm run build
npm run migrate
npm run migrate:verify
```

Чистый пример использует MongoDB на `127.0.0.1:27040`, базу `zarya_clean_local`
и HTTP на `localhost:3001`. Установка сайта использует отдельные порты 27039/3000.
Не применяйте чистую базовую миграцию к базе сайта. Консолидированная схема
в `migrations/0000-schema-migrations.json` предназначена для новой базы;
для баз со старыми отметками миграций требуется отдельная процедура перехода.
См. [ADR 0039](docs/adr/0039-pre-release-schema-baseline.md).

Создайте администратора в интерактивном терминале Git Bash/Bash:

```sh
bash scripts/create-admin.sh
```

Скрипт запросит email и скрытый пароль. Учётные данные не передаются в аргументах
или переменных окружения; готовых учётных записей и паролей нет. См.
[контракты администраторов](docs/arch/administration-users.md) и
[аутентификацию](docs/arch/admin-authentication.md).

Для серверной установки через Docker запустите из каталога установки в
интерактивном терминале после сборки образа приложения, запуска MongoDB и
применения миграций:

```sh
./create-admin
```

Скрипт запускает то же интерактивное создание пользователя внутри контейнера
приложения. Настройка сервера описана в [руководстве по установке](docs/installation/ru/INSTALLATION.md).

После сборки HTTP-приложение запускается из IDE командой `npm run start:http`;
админка доступна на `http://localhost:3001/admin/`. Команда `npm start` открывает
доверенный локальный контекст без HTTP-сервера. Для разработки интерфейса
`npm run dev:admin` запускает админку на `localhost:5173` с проксированием API.

Для одной установки запускается один экземпляр HTTP-приложения. Перед запуском
из IDE или PowerShell остановите Docker-приложение командой
`docker compose stop app`, оставив MongoDB работающей. Нативный и Docker-экземпляр
приложения не должны одновременно использовать одну установку: у них общий
HTTP-порт и файлы координации.

Итог сборки показывает время всей цепочки backend/runtime/admin дополнительно
к времени админки в Vite. Сообщение готовности HTTP показывает время от старта
Node, включая загрузку модулей и дочерних процессов, фактический TCP-сокет
и ссылки на общую админку и раздел каждого сайта. Сокет не является ссылкой на
главную страницу. Координатор читает выбранные Local HTTP-адреса на loopback из
БД и открывает их порты вместе с основным слушателем. Недоступная БД или занятый
локальный порт отменяют запуск. В списке сайтов отмечены готовые локальные
слушатели и адреса, требующие внешней маршрутизации; ссылки на админку сохранены.
После создания сайта или изменения локального порта нужен перезапуск HTTP.
Для Public/HTTPS требуется настройка прокси/TLS. Неопубликованный путь, включая
отсутствующую главную страницу, возвращает 404 даже при работающем слушателе.
См. [ADR 0090](docs/adr/0090-local-site-http-listeners.md).

Содержимое сайтов и дополнительные бизнес-интеграции разрабатываются в отдельных
проектах. Не добавляйте тестовый контент или бизнес-пакеты в чистую поставку.
Сайт создаётся через админку установки; выдача документов не требует аддона.

## Процессы сайтов, CPU и дампы

`npm run start:http` запускает один координатор CMS и отдельный пул обслуживающих
процессов каждого сайта через `child_process.fork`, без PM2 и Node.js cluster. Запросы распределяются по зарегистрированному
адресу сайта; процессы другого сайта не используются как запасные. Координатор непосредственно запускает процессы сайтов и дампов,
обслуживает управление и единственный фоновый обработчик hook. При уменьшении
пула текущие запросы завершаются; новые процессы получают запросы только после
инициализации. «Настройки / Общие» показывает все сайты, назначенные и работающие
процессы, ошибки применения и фактический режим дампа выбранного сайта. CPU-квота,
целое число процессов и измеренная загрузка — разные величины. Назначение
процессов не закрепляет за сайтом исключительные физические ядра.

Во время публикации сайт остаётся доступным: новая версия полностью собирается и
проверяется рядом с действующей, затем одна запись в БД атомарно переключает
активную версию. Обслуживающие процессы продолжают работать. Запросы, выбирающие
версию после переключения, получают новую; уже выполняющиеся завершаются со старым
HTML, планами и сохранёнными ресурсами. Ошибка сборки оставляет действующую версию
активной. Это относится к статическим и Request-страницам, включая прогретые кэши
нескольких процессов. См. [публикацию и аварийные проверки](docs/arch/fork-publication-and-failure-tests.md).

Размещение БД задаётся явно через `ZARYA_DATABASE_PLACEMENT`:
`ManagedLocal` — отдельные управляемые квоты локальной MongoDB и CMS;
`UnmanagedLocal` — локальная БД под отдельным управлением, с обязательным
`ZARYA_CMS_CPU_BUDGET`; `Remote` — внешняя БД, CPU которой не вычитаются
из бюджета машины приложения. Адрес подключения не определяет размещение.
Docker/ОС ограничивает ресурсы установки, координатор управляет числом процессов.
Координатор, сайты и дампы разделяют бюджет CMS; отдельное целое ядро для
координатора не вычитается.

Для управляемой локальной БД по умолчанию выделяется бюджет 1 CPU для БД и по одному процессу каждому сайту;
остаток остаётся нераспределённым. Дополнительный сайт получает процесс и при
превышении рекомендации, с пояснением о совместном использовании CPU, памяти и
соединений. Рекомендация равна доступному CMS CPU-бюджету, округлённому вверх,
и не является жёстким пределом числа процессов. Расчётный расход памяти и
суммарное число соединений не ограничивают назначение процессов. Общий предел
памяти контейнера и пулы MongoDB настраиваются отдельно.
В «Настройки / Общие / Ресурсы» можно менять максимум пула каждого процесса сайта
без ручного перезапуска, в том числе при 1–2 CPU. Сохранённый и фактически
применённый размеры показаны отдельно. Процессы заменяются по очереди, после
готовности новых. `ZARYA_MONGO_MAX_POOL_SIZE` задаёт начальное значение и отдельный
служебный пул координатора при запуске; по умолчанию 5. Соединения мониторинга
драйвера учитываются дополнительно; максимум относится к каждому узлу БД. См. [применение настройки пула](docs/adr/0084-live-site-database-pools.md). На одном CPU БД и сайты работают совместно,
распределение менять нельзя. Для одного сайта с управляемой локальной БД на двух CPU распределение также
фиксировано: 1 CPU для MongoDB и один процесс сайта. Настройка пула БД остаётся доступной.
Для [проверенных профилей с локальной БД](docs/arch/database-pool-benchmark-2026-11-14.md)
при 1–2 CPU рекомендуется начать с пула 2 на процесс сайта; автоматического правила по CPU нет.

При создании дампа сайта или всей установки учитывается число процессов выбранного сайта:

| Состояние сайта и свободного ресурса | Создание дампа |
| --- | --- |
| От двух обслуживающих процессов | Один процесс сайта завершает запросы и останавливается. Вместо него запускается процесс дампа, после завершения восстанавливается процесс сайта. Остальные продолжают отвечать. |
| Один процесс | Дамп выполняется в процессе сайта. На время операции сайт может подвиснуть. Дополнительный процесс не создаётся. |

Допуск записей и подготовка дампа согласованы между процессами. Сайт запрашивает дамп через IPC;
координатор запускает дочерний процесс и дожидается его завершения и очистки
до восстановления мощности сайта. При сбое запрашивающего процесса дамп
отменяется, его блокировки согласованно освобождаются. Отдельный процесс
не устраняет конкуренцию за БД и диск. Восстановление сохраняет общий
режим обслуживания. Неудачный запуск замены отображается как нехватка работающих
процессов. При неопределённом результате запроса обновите список дампов перед
повторным созданием.

CPU-графики находятся на отдельной вкладке **Настройки / Загрузка логических CPU**.
Сбор подключается после входа администратора и продолжается между разделами.
Каждый логический CPU имеет отдельный график с интервалом в секунду.
Последние 300 точек хранятся только в браузере; сервер не сохраняет историю,
не воспроизводит прошлые измерения и не пишет их в журнал. После отключения
последнего администратора сбор прекращается. Пропущенные измерения показываются
как недоступные. Это счётчики всего хоста/VM, включая сторонние нагрузки, а не
загрузка отдельных сайтов и не карта физических ядер. Время отображается в
настроенной IANA-зоне сайта.

В ресурсах отдельно показаны общая CPU-квота, введённые значения, сохранённое
распределение и работающие процессы. Рекомендацию по CPU можно превысить с
предупреждением. Расчётного предела по памяти и соединениям нет. Фактический
сбой запуска показан отдельно от сохранённого количества процессов. Результат сохранения или отказ виден рядом с кнопкой.

В управляемом production Compose CPU-квоты MongoDB и CMS применяет и проверяет
ограниченная локальная служба helper. Docker-сокет подключён только к ней;
обслуживающие процессы обращаются через закрытый Unix-сокет с ключом доступа.
Настройки записываются в `.secrets/resources/compose.json`, подключённый через
`COMPOSE_FILE`, поэтому пересоздание контейнера сохраняет квоты. В неуправляемом
или нативном окружении изменение квот явно недоступно. Сокет и ключ должны
оставаться приватными. Helper — отдельная Node.js-служба управления Docker.
Процессами сайтов, дампами и сбором CPU-счётчиков управляет координатор CMS.
Перед сборкой Compose выполните
`node scripts/prepare-compose.mjs`: версия `ZARYA_CMS_VERSION` берётся из
`package.json`, существующие секреты и распределение сохраняются.
`node scripts/release-consistency.mjs --image IMAGE:0.15.0` проверяет тег и
версию действительно собранного образа. Так же проверяется образ executor.

Оба Compose закрепляют MongoDB 9.0.8 одинаковым неизменяемым digest. Перед
изменением существующей установки прочитайте
[архитектуру fork](docs/adr/0083-fork-supervision-and-database-placement.md),
[контракты ресурсов](docs/arch/0.14.0-site-process-allocation.md) и
[порядок обновления MongoDB](docs/arch/mongodb-9-upgrade.md). Автоматическое
обновление работающей БД этим не разрешается.

## Калибровка ресурсов

В «Настройки / Калибровка» создаются профили нагрузки и запускается подбор
настроек при работающих сайтах. Профиль показывает все сайты; изначально 100%
запросов поровну распределяются между их главными страницами.
Кнопка «+» добавляет URL, относительный путь или числовой ID страницы с долей
запросов. Доступны сотые доли процента; пустое значение сохраняется как ноль.
Сумма выше 100% запрещена, меньшая положительная сумма при запуске
пропорционально приводится к 100%.

Для запуска нужны управляемые квоты Docker. Общий CPU-бюджет профиля реально
делится между БД и CMS во всех замерах, включая отправную точку. Подбираются
дробные CPU БД, пул и число процессов каждого сайта. Перед нагрузкой проверяются
фактические квоты. Без управления CPU запуск недоступен; старые замеры при
фиксированных ресурсах явно помечены в истории.
Диапазоны поиска, длительность и критерии редактируются; исходный критерий —
p95 не больше 600 мс. После замеров исходные настройки восстанавливаются.
«Настройки / Основные» показывает последние десять прогонов с кнопкой
«Применить»; завершение калибровки само настройки не применяет.
См. [режимы, измерения и восстановление](docs/arch/resource-calibration.md).

## Установка и автоматическая доставка

Следуйте [инструкции установки](INSTALLATION.md): Docker-окружение, приватные
настройки, MongoDB, домены/TLS, обновление и восстановление. Настройте цель сайта
на вкладке **Настройки / Деплой**, затем запустите отдельный исполнитель.
Зафиксированные публикации, включая изменения только маршрутов, запускают
доставку автоматически. Сохранение черновика не запускает доставку. Админка
показывает активную публикацию CMS отдельно от подтверждённой внешней доставки,
диагностику и повтор. Реквизиты провайдера хранятся в окружении исполнителя.

См. [настройку Cloudflare](docs/installation/ru/cloudflare.md) и
[контракты деплоя](docs/arch/deployment-contracts.md) и
[публикацию Markdown/JSON-LD](docs/arch/markdown-and-json-ld.md).

## Ручная доставка в Cloudflare

Перед ручными командами остановите автоматический исполнитель и завершите
или согласуйте текущую загрузку.

Cloudflare хранит статические файлы, а отдельный Node.js-бэкенд с MongoDB
обслуживает API, админку и Request-страницы. Выполняйте команды в проекте сайта,
где доступны его база, публикации и медиа. В чистой поставке нет опубликованного
сайта. Бэкенд запускается через `npm run start:http` с настройками MongoDB в `.env`.

1. Скопируйте `cloudflare.example.json` в `cloudflare.json`. Укажите `siteId`
   из URL сайта в админке, постоянное имя `workerName`, HTTPS-адрес `publicOrigin`
   и отдельный доступный HTTPS-адрес `backendOrigin`. Примеры localhost
   предназначены для локальной проверки. Выберите публичный адрес в настройках
   сайта и задайте административный origin в `ZARYA_ADMIN_AUTH_ORIGIN` бэкенда.
2. Задайте одинаковый случайный `ZARYA_EDGE_PROXY_SECRET` в окружении команды
   деплоя и в `.env` бэкенда. Команда передаст его в секреты Worker. Авторизуйте
   Wrangler через `npm exec -- wrangler login` либо задайте
   `CLOUDFLARE_ACCOUNT_ID` и `CLOUDFLARE_API_TOKEN` в приватном окружении.
3. Опубликуйте сайт в CMS и подготовьте комплект без выкладки:

   ```sh
   npm run cdn:prepare
   npm run deploy:cloudflare -- --dry-run
   ```

4. Для первой выкладки и последующих обновлений выполните:

   ```sh
   npm run deploy:cloudflare
   ```

Папка статики — **`deploy/public/`**. Конфигурация Worker и маршруты создаются
в `deploy/`; выбирать внутренний номер релиза не нужно. Экспорт не публикует
черновики и не запускает сервер CMS. Статические HTML/CSS/JS и публичные медиа
попадают в Cloudflare; Request-страницы и API работают через бэкенд без кеширования
ответов. Публичные файлы крупнее 25 MiB остаются на бэкенде; команда сообщает о них.

После изменения содержимого сначала опубликуйте его в CMS, затем повторите
команду выкладки. Изменения данных API не требуют выкладки статики. Подготовка
и `--dry-run` ничего не развёртывают. Подробности и ограничения — в
[контракте Cloudflare](docs/arch/cloudflare-deployment.md).

## Аддоны из GitHub

На странице Add-ons сайта укажите URL публичного репозитория GitHub и нажмите
Install. CMS загрузит `addon.runtime.gz` из последнего стабильного релиза,
проверит пакет и активирует его без перезапуска. Пакет появится в общем каталоге;
для каждого сайта его нужно включить отдельно.

Сборка и выпуск пакета описаны в [руководстве по разработке аддонов](docs/addon-development/README.md).
Поддерживаемые форматы и поведение CMS описаны в [контракте установки](docs/arch/site-addons-contracts.md#repository-release-installation).
